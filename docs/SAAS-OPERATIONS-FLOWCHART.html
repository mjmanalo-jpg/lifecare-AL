Release Engineering

Supabase + Prisma Migration Release Gate

A controlled staging rehearsal must pass every gate before production or a second customer is enabled
Release sequence
1

Restore backup to staging

Verify that the backup can actually be restored. Never rehearse on production.

2

Confirm connections

DATABASE_URL / DIRECT_URL must target the intended Supabase project; encode reserved characters.

3

Validate + inspect status

npx prisma validate   npx prisma migrate status

4

Baseline only if proven

For former db push databases, resolve old migrations only after confirming their columns exist.

5

Deploy migrations

npx prisma migrate deploy — foundation first, tenant RLS second. Never use db push.

6

Run backfill report

Stop on missing ownership, cross-tenant links, orphaned PHI, duplicates or count mismatches.

7

Configure runtime role

Use a non-owner PostgreSQL login with rolsuper=false and rolbypassrls=false.

8

Provision Platform Admin

Link immutable Supabase Auth UUID, confirm email, enroll MFA and replace the temporary password.

9

Deploy application

Runtime uses least-privilege URLs. Migration-owner credentials remain deployment-only secrets.

10

Run isolation matrix

Two organizations, multiple communities, all roles, APIs, exports, aggregates and guessed IDs.

11

Test authenticated Realtime

Keep tenant Realtime disabled until API and direct RLS tests pass with the application role.

12

Release + observe

Monitor 401/403/404, entitlement denials, invitation failures and RLS violations before customer two.

Hard release decision

Are migration reconciliation, isolation tests and backup restoration all successful?

All three conditions are mandatory. “Mostly passing” is not a release state.

→

NO · Stop rollout

Preserve diagnostic output, restore the rehearsed backup, investigate, correct and repeat the full gate sequence. Never edit _prisma_migrations manually.

→

YES · Controlled production release

Enable customer access, retain monitoring, and only enable tenant Realtime after authenticated policies are proven.

Acceptance checklist

Data integrity

Organization/community ownership reconciles; tenant-aware uniqueness holds; no ambiguous resident, membership or access mappings remain.

Isolation

Reads, writes, includes, aggregates, exports, search, FastAPI, RLS and Realtime cannot cross organization or community boundaries.

Operational recovery

Suspension blocks normal access, audit remains available, backup restoration succeeds, and production/staging/demo remain separated.

Defense in Depth

Runtime Authorization, Isolation & Tenant State

Every request is evaluated through identity, MFA, membership, entitlement and PostgreSQL RLS boundaries
Request authorization path

1 · Authenticate

Validate Supabase identity and signed LCMS session.

→

2 · Verify MFA

AAL2 required for platform and organization admins.

→

3 · Load access

Platform, organization, community and resident memberships.

→

4 · Check plan

Module entitlement, subscription state and usage limits.

↓

5 · Establish tenant context

Server chooses validated organization/community. Client-supplied ownership fields are ignored or rejected.

→

6 · Execute with RLS

Transaction-local user, organization and community context is set using the non-BYPASSRLS application role.

→

7 · Return + audit

Only tenant-safe results are returned. Sensitive successes and denials create immutable, PHI-minimized audit events.

Tenant lifecycle state machine

TRIALING

Limited evaluation

ACTIVE

Normal access

PAST_DUE

Contract follow-up

SUSPENDED

Normal access blocked; data preserved

CANCELED / ARCHIVED

Retention and export rules apply

Platform recovery

Explicit, audited operator action only; support metadata does not automatically reveal resident PHI.

→

Reactivate

Validate subscription, memberships, security state and tenant context before access resumes.

Safe denial outcomes

401

Invalid or expired identity/session

403

Known user lacks role, MFA or entitlement

404

Hide another tenant’s resource existence

409

Tenant-aware uniqueness or capacity conflict

422

Invalid relationship or tenant mismatch

RLS deny

Missing/wrong transaction tenant context
